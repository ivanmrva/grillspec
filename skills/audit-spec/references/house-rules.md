# House rules — shared by every engine

The rules identical across interview, derivation, and execution. Each engine adds only what is specific to its kind of work.

## The workspace is the only source of truth
Work from the **working tree exactly as it exists now** — the spec, code, and tests on disk. Never treat git history (commits, `git log`/`git show`, stashes, branches, reflog) as a source to reconstruct from: a removed file is gone, not a recoverable draft; "it used to work" is settled by the current tree. Git *mechanics* are fine — branching and committing per the workflow, `git bisect` to localise a regression, `git diff` to identify a change set — the fence is about what you treat as the baseline. Likewise never read or write outside the project folder (no parent dirs, home dir, sibling repos, absolute paths beyond the workspace root) unless the user explicitly hands you that input. Prior work that appears to be missing is a finding or blocking gap to surface — never a cue to restore it from history or from outside the folder.

## Artifacts are timeless
A record under `spec/` — and every ADR — states what is true now, never the document's own history. A reader has no idea it was generated, by what tool or in how many passes, so leave no development trace: never tag content with its edit history (`new` / `newly added` / `now` / `previously` / `no longer` / `renamed from` / `expand→contract`), never note what this pass added, moved, cut, or deferred, never write `this round` / `this iteration` / `as discussed`. A forward-looking scope choice is stated as a timeless property (an exclusion ADR, or `deferred until <trigger>`), not as "what we deferred this time". The same word stays legitimate as domain language (a `new booking`); it is banned only when it narrates the document's own evolution.

The same holds for **structure**: when a change lands, integrate it where it belongs and re-author the affected sections so the whole reads as one coherent document written in one pass. Never bolt additions onto the end (an addition's place is wherever it belongs, frequently mid-document), never spawn a parallel section — or a separate paragraph, note, or row — beside content that already owns it: a change that modifies an existing statement rewrites that sentence, field, or row in place; only genuinely new information becomes new content. Never leave a document half-restructured. Emphasis follows the document's convention for its meaning (a defined term, a field label, an ID) — never to flag that something is new or changed. (A transient run-report back to the orchestrator may of course say what changed — that is not a `spec/` artifact.)

## Output discipline
Write your artifact to the location you're given, or — with none — your standalone default folder. ADRs go in the shared `adr/` folder (at the spec root; your working root when standalone), each prefixed with your area code (`ADR-<AREA>-NNN`) so two skills never collide. No side-ledger files: an open point is resolved into the artifact or, if a deliberate choice, an ADR — there is no separate open-questions, resolutions, assumptions, or risk file. Your output is the project's documentation and has no awareness of this system: never name a skill (`grill-*`, `derive-*`, an orchestrator) or a tool, and never narrate how a file was produced.

Every file under `spec/` opens with its `<!-- scope: … | excludes: … | format: … -->` header (code under `src/`+`tests/` does not). Style: tight, structured, ubiquitous language; **prefer a Markdown table whenever the content is even loosely tabular** — anything repeated over a set of items (fields, statuses, IDs, mappings, results, actor×permission) is a table, not a bullet list or prose. Typed fields and short bullets carry what isn't tabular; fenced code or a small diagram where they fit better. A clarifying sentence is fine; walls of prose, filler, hedging, and restating are banned — a line that carries no required fact is deleted. (Only an ADR's rationale may run one to three terse sentences.) When you target an external standard, format, or protocol (a WCAG level, OpenAPI, OAuth), target its **current / latest stable** version — never a pinned historical one, unless a user or constraint pins it.

## Stable IDs
Every referenceable element carries a stable, immutable, type-prefixed ID; reference by ID, never by restating; supersede, never rename or reuse. Two mechanical rules the traceability spine depends on:
- **Bare type prefix, never context-namespaced.** `AGG-250`, never `SUR-AGG-250` — consumers key on the leading prefix, so a namespaced ID silently fails to register as a definition. Disambiguate in the suffix (`AGG-SUR-250`) or by disjoint numeric bands per context.
- **The ID is the row key — leading column.** A name-first row (`| pay-invoice | CMD-170 |`) does not register `CMD-170` as defined, and every later reference to it reads as undefined. ID first, name second.

## System friction → plugin feedback, never your artifact
If you hit a defect or gap in this system itself — a check that's demonstrably wrong, an instruction you can't satisfy, an ID type the tooling rejects, a path the structure won't allow — don't silently work around it and don't put it in your artifact. Append it: `python3 scripts/plugin_feedback.py --add --kind bug|gap|improvement --component <this skill/the tool> --summary "…" --suggest "…" --evidence <file:line>` — it writes `GRILLSPEC-FEEDBACK.md` at the project root, outside `spec/`. Capture-and-route for the plugin author; never self-patch. Bar: a real contradiction or an unsatisfiable rule, not a preference.
