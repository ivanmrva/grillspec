# derive-tasks — worked example

A single implementation-final task manifest — **one uniform `field | value` table**; the two sub-structured fields (`behavior`, `tests`) carry their structure **inside their cell** with `<br>` line-breaks:

```markdown
# T-014 — Pay an order (vertical slice)

| field | value |
|---|---|
| phase | MVP · afk: eligible |
| outcome | a buyer pays an order and sees a receipt |
| behavior | UC-014 pay an order<br>· AC-014a a valid payment is accepted and a receipt is shown<br>· AC-014b a zero / over-amount payment is rejected with a clear error |
| domain | AGG-Order · CMD-Pay · EVT-OrderPaid · INV-Order-total>=0 |
| data | DATA-03 (payment record; retain 7y) |
| api | API-Pay (POST /orders/{id}/payments) |
| ux | JRN-07 (pay-flow) on SCR-05 (checkout) — states: confirm-dialog · spinner · receipt · error · permission-denied → prototype: prototypes/ui/pay.html (frozen at finalization — see prototype-review) |
| a11y | keyboard tab→confirm · focus trap in dialog · WCAG SC 2.4.7 (focus visible), SC 3.3.1 (error identified) |
| security | SEC-03 (only Owner/Billing may pay — deny path: Viewer's pay attempt rejected + tested) · OBL-02 (payment record kept 7y) · ENTL-04 (pay is a paid-tier capability — over-limit + lapsed-billing deny path tested) · validate amount > 0 |
| nfr | ASR-002 (p95 < 300ms) |
| obs | SLO-2 payment-latency histogram + payment_failed structured event · AEV-2 checkout_completed analytics event (serves EXP-3) — each emitted AND asserted |
| integration | PSP-Stripe (charge — incl. timeout/5xx degradation path) |
| placement | billing context · src/billing/{api,app,domain,infra} |
| design | inline (CRUD-shaped over the aggregate — no hard algorithm/concurrency, so no design-first pass) |
| prototype-review | frozen — reviewed at finalization: prototypes/ui/pay.html was clicked-through + tweaked before the wave (realises the ratified JRN-07 states). An unreviewed / JIT screen, or one introducing an unratified visual/UX choice, is instead afk: blocked — visual/UX review pending (or `waived — <why>` to consciously skip review) — a non-N/A ux slice never auto-AFKs this gate |
| tests | fixture: seeded order — one `<br>`-line per AC, `AC-id — tiers — test intent`:<br>AC-014a — unit · contract · e2e — valid charge → receipt; contract on API-Pay<br>AC-014b — unit — amount ≤ 0 / over-amount rejected with a clear error |
| deploy | ships behind FLAG-pay to dev (first env of the promotion path) — or N/A — no new deployable surface |
| human-prereq | N/A |
| depends | T-002 (order aggregate) |
| DoD | standard gate — the Verification Record regenerated by `check_task_record.py --init` (tests-first · tests:layers · coverage · mutation · fitness:no-fakes · fitness:architecture · spec-lint · deploy · ux:states · a11y · ux:rendered · prototype-review · obs · conformance · traceability); deltas: coverage 85% · mutation 70% (TEST-STRAT) |
```
Every dimension resolved (or N/A) → the agent can implement with zero ambiguity. Note the **ID-keyed shape**: `behavior` is one `<br>`-line per `UC-` with its `AC-`s on following `<br>`-lines; `tests` is **one `<br>`-line per AC inside the single `tests` cell** (`AC-id — tiers — intent`, never a prose blob and never a "see table below" pointer — the third segment is the *test intent*, and the line is what `check_task_record.py` reconciles against the test tree, where a literal `@covers AC-id` tag must live in the failing-capable test source that pins it); `ux` references the journey by **`JRN-` id** + the interaction-states this slice realises; and **`DoD` is a *reference*, not a restatement** — it points at the standard gate (the per-task **Verification Record**, regenerated from the frozen refs) and spells out only the **task-specific deltas**, so a hand-authored line can never silently undersell the enforced bar (conformance, deploy, fitness, mutation all live in the gate). `design: inline` here because the slice is CRUD-shaped; a slice with a **hard algorithm · real concurrency · a cross-context saga** would be `design: design-first`, and its module internals get a JIT impl-design pass before coding. The **prototype is reviewed at the `prototype-review` gate before code** — for a non-`N/A` `ux` slice like this one, `afk: eligible` requires the prototype to be **frozen (human-reviewed at finalization)** or an explicit `prototype-review: waived — <why>`; an unreviewed / JIT-generated screen (or one introducing a new visual/UX decision) is `afk: blocked — visual/UX review pending`. Auto-AFK of this gate is reserved for slices whose `ux` is `N/A` (headless or `N/A — reuses DS-…`). (`lint_spec.py` check #30 enforces this: an eligible non-`N/A`-`ux` slice must read `frozen`/`reviewed`/`waived`.) If the slice UX weren't yet defined, this task is *not* final — derive-and-ask the flow, record the `JRN-` + states here, then ship.

## A credential-gated slice + the provisioning register

A slice that needs an external credential names it by its **`environments.md` key** (the register join token), and is `afk: blocked` until that credential is `provisioned`:

```
| phase | MVP · afk: blocked — external credential (STRIPE_SECRET_KEY pending) |
| ...
| integration | PSP-Stripe (charge) |
| human-prereq | Stripe API key → key `STRIPE_SECRET_KEY`, set in CI + platform secret store (steps: bootstrap.md §Stripe) |
```

The credential's live state is the spec-root `_provisioning.md` register (authored, layer-free — it maps an infra credential to its delivery tasks and holds state that must survive task re-derivation):

| key | dependency | owner | consumed-by | state | evidence |
|---|---|---|---|---|---|
| `STRIPE_SECRET_KEY` | Stripe account + API key (`prerequisites.md`) | human | T-014, T-021 | pending | — |
| `RESEND_KEY` | Resend transactional email | human | T-046 | provisioned | set in CI 2026-06-30 |

Now the machine can decide: `T-046` may be `afk: eligible` (its `RESEND_KEY` is `provisioned`); `T-014` must stay `afk: blocked` while `STRIPE_SECRET_KEY` is `pending` — and `autorun` parks it **before** the wave instead of discovering it mid-slice. When the human provisions Stripe, `autorun` flips the row to `provisioned` (+ evidence), which unlocks T-014/T-021 for the next wave. `lint_spec.py` enforces the same invariant statically: an `afk: eligible` task whose credential prereq isn't `provisioned` here is a finding. **Never** let a task claim eligibility on a free-prose ‘arrives via T-001’ — only a `provisioned` register row backs it.
