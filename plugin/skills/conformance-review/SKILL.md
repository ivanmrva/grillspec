# conformance-review

**Load `${CLAUDE_PLUGIN_ROOT}/grill-shared/exec-engine.md` first and follow it.** This skill: **the post-task review of generated code against the spec**, run after each task, before the next. **(A) conformance** (code vs spec, architecture, contracts, security, NFR-evidence, traceability — *blocking*); **(B) design health** (deepening opportunities — *advisory*). Distinct from, and complementary to, the current agent host's native code-review workflow.

## Process
1. **Set the scope.** `changed` (default, every task — the task's changed code + its blast radius: callers, callees, seams) or `full` (a wider on-demand re-check — the whole codebase, still checked incrementally). The checks are identical; scope changes only *which* code they see. **`full` is still this same build-time, self-certifying review, just over more code — it is NOT the release audit.** The independent, adversarial, whole-build attestation (that the per-task gates were genuinely run and backed, cross-task coverage survival, suite-shape-vs-declared-distribution, operate-ledger reconciliation) is a separate whole-build audit — a self-certifying review cannot audit its own ledger. Preparing to ship is that audit's job, not `--full`.
2. **Run Lens A — conformance (blocking).** Architecture first (the hardest check): dependency direction & acyclicity, **each module's actual dependency direction matches its declared `role:`** (domain/driving-port/driven-port/adapter/application-service — once the implementation design records it), context-boundary integrity, layer isolation / ports & adapters, interface conformance, no structural rot, and a structural-regression scan of this diff. For a slice touching a cross-module/cross-context flow, **confirm the implementation follows the architecture's key sequences** (`arch/sequences.md`) — the golden path AND its failure/compensation branches (a sequence nobody re-reads is a sequence nobody follows). **Confirm every ASR fitness function `arch/quality.md` names exists as an executable rule** — a named-but-never-authored fitness function is an unenforced ASR wearing a green gate row. **Confirm the shipped pipeline matches the ratified promotion hops + per-hop gates** (`infra-ops/cicd.md`) **and the runtime contract holds** (the `preflight` doctor command, health/readiness endpoints, and startup order `conventions/runtime-contract.md` declares actually exist in the artifact). Then the spec: boundaries, contracts (`API-`), data model + residency/retention (`DATA-`) **including the retention/TTL/deletion triggers the slice owns**, security rules, obligations & entitlement gates (`SEC-`/`OBL-`/`ENTL-`) — **"evidenced" means the deny / over-limit / lapsed-billing path is exercised by a test, not that middleware exists**, NFR/ASR with **test evidence, not an assertion**, the `obs` cell's signals (the `SLO-`-backing telemetry and `AEV-` analytics events **emitted and asserted**, so the spec'd measurement actually exists), any `ML-` capability's **eval-harness evidence measured against its stated bar**, and — for a slice with a non-`N/A` `ux` dimension — **UI conformance judged on the RENDERED surface, never by code-reading alone**: run the app, open every screen the slice touches, and **walk the journey's `SCR-` screen path from `prototypes/ui/flows.md`** — compare against the **frozen prototype** (layout & composition, microcopy, every interaction state the `ux` cell names actually reachable and realised), confirm styling flows only through `DS-` tokens/components (no raw values / bespoke styles), walk the `a11y` cell's keyboard/focus path yourself, and render at the design-system breakpoints — **a screen you never rendered is a screen you never reviewed**, and the `ux:states` / `a11y` / `ux:rendered` record rows must carry real evidence (the scan output, the render run), not assertions. **A slice claiming `ux: N/A — reuses DS-… on SCR-NNN` still gets the rendered check on that screen** — the reuse classification exempts it from the prototype-review gate because the IA + design system determine the change, not because nobody looks; open the touched screen and confirm the claim (a composition/flow change hiding behind a reuse claim is a blocking mis-classification). **Scan the production tree for non-production code** (`check_no_fakes.py` is the mechanical first pass; you add the semantic judgment) — a stub/mock/in-memory double/canned response/`TODO`-short-circuit/unwired-fallback shipped in `src/` is a blocking violation **even when every test is green** (green-against-a-fake is the trap this lens exists to catch); test doubles belong only under `tests/`. **Scan the deploy/CI surface the same way** (`check_deploy_real.py` is the mechanical pass) — a faked or skipped deploy (an `echo`/`exit 0` job, a `# TODO: deploy`, a commented-out or `if: false` step, or a deployable slice whose deploy was silently omitted "because infra isn't ready") is the same blocking violation; the deploy scripts/CI/IaC are production code held to the production-only bar, and a slice that reports done while its pipeline can't actually ship has not conformed. **Confirm the deploy is behaviourally proven, not just statically present** — the slice's e2e/smoke ran **against the real deployed environment** (the preview/e2e/staging env named in the test strategy), **not** a local `docker-compose`/testcontainers stack (that's integration mislabelled and proves nothing about the deploy); the `deploy` row's evidence is that green run. If the env genuinely can't run yet, the row is `blocked — <env> not provisioned` (escalated), never a `PASS`. **Scan any schema/data change the same way** (`check_migration_real.py` is the mechanical pass) — a faked or empty migration (a `-- TODO`, an `operations = []`, a DDL-less `.sql`, a `pass`-only `up()`) is a blocking violation just like a missing one; a migration is production code that must actually change the schema/data it claims to. **Scan the test suite for disabled or narrowed tests** (`check_no_skips.py` is the mechanical pass) — a `skip`/`xfail`/`.only` marker, or a CI test step that swallows a red, is a blocking violation; and for the slice's e2e, **enumerate the spec paths it does NOT exercise**: list each referenced `AC-`/flow branch (main + alternate) the e2e leaves untouched and require a stated reason per omission — an assumption-driven avoidance ("the broker might not be ready, so the test steers around it") is a blocking violation exactly like a skip, while a justified omission (covered at a cheaper tier per the test strategy) is recorded and passes. Forcing the enumeration is the point: a weakened e2e survives "don't avoid paths" prose, but not an explicit not-exercised list. Confirm **traceability** in BOTH directions: every referenced spec ID has implementing code + a passing test, **and every behavior in the diff has a driving spec ID** — sweep the changed code and tests for behavior nothing referenced demands (`check_orphan_tests.py` is the mechanical pass over the test tree: no orphan test source, no dangling `@covers`; you add the code-side judgment for behavior no test pins at all). An undriven behavior is **drift — a blocking violation even when the user asked for it in chat** (chat is spec input, not code input): route it back spec-first — mint/amend the driving ID in its owning area and the task manifest, then re-land — never wave it through because it was instructed.
3. **Decide the verdict.** `VERDICT: PASS` only when Lens A is fully clean; else `VERDICT: FAIL — <blocking violations>` → fixed inside the boundaries. If the spec itself is wrong, raise a gap — never bend code around a bad spec, never edit the spec to match the code.
4. **Run Lens B — design health (advisory).** Surface shallow modules that could become deep (the deletion test; the interface is the test surface; one adapter = a hypothetical seam, two = a real one). Note friction organically. Never blocks the verdict.
5. **Record + reconcile the Verification Record.** Write the traceability matrix + the review report (blocking-violation list + prioritized design-candidate list); a `PASS` here **is** the independent `VERDICT: PASS` the task's Verification Record (`spec/10-delivery/verification/tasks/T-NNN.md`) cites for its `conformance` obligation. Then run `python3 ${CLAUDE_PLUGIN_ROOT}/tools/check_task_record.py spec --task T-NNN`: it mechanically confirms the record's `status: done` is backed — every referenced obligation evidenced, every `AC-` traced to a passing test, no dropped/under-bar obligation. A red checker is a blocking `FAIL` regardless of the semantic review. Cheap design candidates: refactor now under green; larger ones become focused-change tasks.

## Rules
- **Architecture conformance is first-class** — a failed-test re-run is exactly when shortcuts creep in, so check STRUCTURE every run, not just behavior: dependency direction & acyclicity · **role/direction match** (each module's real dependencies obey its declared `role:`, inward only) · context-boundary integrity (cross-context only via a published contract/event) · layer isolation & ports/adapters (persistence behind a port, no ORM/DTO leak, depend on interfaces) · interface conformance (no public surface beyond the implementation design) · no structural rot (no duplication, god-class, layer bypass, dead code, or hack to go green). The fitness functions enforce the deterministic part each run; this skill adds the **semantic** judgment they can't make.
- **Never pass on (blocking → back to implementation):** a crossed context/layer boundary · a dependency cycle · a module whose real dependencies contradict its declared `role:` direction · persistence/ORM leaking across a layer · an interface widened beyond the implementation design · duplicated logic or a layer bypass introduced to pass a test · **a fake/stub/mock/in-memory double/canned response/unwired-fallback shipped in the production tree (`src/`)** — non-production code belongs only under `tests/`, and green tests against it do not redeem it · **a faked or silently-skipped deploy/CI artifact** (an `echo`/`exit 0`/`# TODO`/`if: false` deploy, or a deployable slice that omitted its deploy "because infra isn't ready" instead of escalating) · **a skipped/xfail'd/`.only`-narrowed test or a test-failure-swallowing CI step** (a red laundered into green — `check_no_skips.py` is the mechanical pass; the waiver file is reviewed here, every entry needs a live reason) · **an e2e that avoids a referenced path on an assumption** (an unexercised `AC-`/flow branch with no recorded justification) · a contract mismatch · an unenforced security rule/obligation/entitlement gate — **or one "enforced" by code whose deny/over-limit path no test invokes** · an NFR asserted but not evidenced · **an `obs`-cell signal (telemetry / analytics event) emitted nowhere or asserted nowhere** · **an `ML-` capability shipped without its eval bar met** · **a rendered screen that diverges from its frozen prototype** (a missing/unreachable interaction state · off-design-system styling · a broken keyboard/focus path · a breakpoint that collapses · an a11y scan with criticals — or a UI slice reviewed by code-reading with no rendered check at all) · a schema/data change with no migration · an untraced spec ID · **a changed `src/**` line no test executes, or a diff-mutation score below its bar** (the record's `coverage`/`mutation` rows are diff-scoped — the code→test leg of the triangle) · **behavior in the diff with no driving spec ID** (an ad-hoc instruction implemented past the spec, an orphan test source, or a dangling `@covers` — chat is spec input; `check_orphan_tests.py` is the mechanical pass, and its waiver file `.grillspec/no-orphans-allow.txt` is reviewed here like the no-skips one — every entry needs a live reason).
- **Verdict:** `VERDICT: PASS` only when Lens A is fully clean (every referenced ID traced to code + a passing test); else `VERDICT: FAIL — <violations>`. Lens B never blocks.
- **Vs host-native code review** — native = generic correctness/security/regressions; this = spec-divergence + traceability + architecture-health. Borrow its disciplines: verify each finding against the actual code before flagging; tag every finding by severity (`blocking` · `important` · `nit` · `suggestion`).
- **Lens B vocabulary** — module (interface + implementation) · interface (all a caller must know) · depth (much behavior behind a small interface; shallow = interface ≈ implementation in complexity) · **information leakage** (one design decision spread across N modules, so a change to it edits all N — a candidate to consolidate behind one module). Don't abstract before the second adapter; a rejected design candidate with a load-bearing reason becomes an ADR so future reviews don't re-suggest it.
- **Held-out `AC-` (orchestrated runs)** — when the orchestrated build withheld a subset of the task's `AC-` from the implementer, you hold the full set: author fresh acceptance tests for the held-out `AC-` (or run the Tier-B journey tests that cover them) against the built slice. A held-out `AC-` that fails is a blocking `FAIL` (overfitting to the visible tests) → back to implementation. N/A for a solo run with no orchestrator.
- Code lives in the source tree, never in `spec/`.

## Output
Written under `delivery/verification/`:

| File / target | Captures | Format |
|---|---|---|
| `delivery/verification/traceability.md` | matrix: spec ID → T- → code/test path → pass | — |
| `delivery/verification/review-report.md` | blocking-violation list + the e2e **not-exercised list** (each untouched `AC-`/flow branch + its stated reason) + prioritized design-candidate list + the verdict | — |
